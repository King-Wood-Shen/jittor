## Public training and controlled forward

The public `python -m swift.cli.main rlhf --rlhf_type grpo --advantage_estimator rloo` path ran independently under native PyTorch (23778) and strict `JITTOR_TORCH_SHIM=1` (23789) on the same RTX 4090 worker. It used local Qwen2-0.5B, FP32 eager attention, full tuning, two completions from a fixed arithmetic prompt, the local completion-length reward, SGD at `1e-5`, eight updates over one rollout (`num_iterations=8`), and no checkpoint save. The isolated TRL 0.26.0 overlay and model weights are the same as the accepted GRPO profile. Exact commands, input hashes, per-step captured tensors, gradients, parameter hashes and logs remain in the unversioned `$JITTOR_LAB_ROOT/_state/ms-swift-cuda/20261014-qwen2-rloo-advantage-l02-v1/` directory.

Preflight 23774 failed before training because it selected an old JIT cache and `JITTOR_NO_BUILD=1` correctly rejected it. Corrected preflight 23775 passed native and shim CUDA imports, current-source no-build cache, NFS fsync and a 6 GiB disk reserve for the no-checkpoint stages. Read-only verifier 23795 passed; its predecessor 23794 failed only because the verifier expected a `grad` key on present gradient entries. The scheduler rejected a CPU-only verifier request before assigning a job, after which the verifier used a GPU worker. Neither harness issue is an RLOO compatibility result.

Both public runs constructed the real model, tokenizer, dataset, trainer and optimizer; all 290 initial trainable parameter names, shapes and value hashes matched. Every one of eight steps in each runtime had 290/290 finite CUDA gradients, with nonzero gradient norm. Native changed 252 model parameter hashes and strict shim changed 247. First-two versus last-two mean training loss fell from `-0.001905085` to `-0.024701715` natively and from `-0.005670545` to `-0.074094535` under shim. The first sampled pair had per-token RLOO advantages `+5/-5` natively and `-10/+10` under shim, demonstrating an unnormalized leave-one-out reward difference. Strict shim recorded `cuda=1 fallback=0` at process start and end.

The two public runs sampled different completion token IDs despite identical initial weights, seed and prompt; their per-step loss and gradient values are therefore separate convergence evidence, not same-input numerical parity. To close L1, worker job 23796 loaded the model through ms-swift's `get_model_processor` API and forwarded the **same captured native RLOO token IDs and mask** on both CUDA runtimes. Logits shape was `[2,50,151936]`; mean absolute difference `6.85e-6`, RMSE `1.14e-5`, and losses `1.14406240` native versus `1.14406216` shim. In the same worker job, ms-swift's `compute_advantages` API returned `[-5,5]` on CUDA for fixed rewards `[25,30]`, two generations, RLOO and no reward scaling on both runtimes; strict fallback was zero. These observations establish controlled L1 and independent fixed-window L2 without imposing stepwise equality on sampled training trajectories.

The public CLI completed but deliberately wrote no checkpoint; L3 model, optimizer, scheduler, RNG and dataloader-cursor restoration were not exercised. The existing full-model GRPO checkpoint profile needs at least 8 GiB free for its measured save peak and reserve, while this run's NFS `/home` had about 7.2 GiB free. L3 is resource-blocked for this full-tuning profile until a fresh storage preflight succeeds. Formal L4 and L5 remain open under the ordered L0–L5 contract. Job 23796's forward reuses the known Qwen2 causal-LM mechanism but uses this RLOO run's captured tokens and verifies the distinct RLOO advantage function; it is not another GRPO training experiment.
