## Public training and controlled forward

The public `python -m swift.cli.main rlhf --rlhf_type grpo --advantage_estimator rloo` path ran independently under native PyTorch (23778) and strict `JITTOR_TORCH_SHIM=1` (23789) on the same RTX 4090 worker. It used local Qwen2-0.5B, FP32 eager attention, full tuning, two completions from a fixed arithmetic prompt, the local completion-length reward, SGD at `1e-5`, eight updates over one rollout (`num_iterations=8`), and no checkpoint save. The isolated TRL 0.26.0 overlay and model weights are the same as the accepted GRPO profile. Exact commands, input hashes, per-step captured tensors, gradients, parameter hashes and logs remain in the unversioned `$JITTOR_LAB_ROOT/_state/ms-swift-cuda/20261014-qwen2-rloo-advantage-l02-v1/` directory.

Preflight 23774 failed before training because it selected an old JIT cache and `JITTOR_NO_BUILD=1` correctly rejected it. Corrected preflight 23775 passed native and shim CUDA imports, current-source no-build cache, NFS fsync and a 6 GiB disk reserve for the no-checkpoint stages. Read-only verifier 23795 passed; its predecessor 23794 failed only because the verifier expected a `grad` key on present gradient entries. The scheduler rejected a CPU-only verifier request before assigning a job, after which the verifier used a GPU worker. Neither harness issue is an RLOO compatibility result.

Both public runs constructed the real model, tokenizer, dataset, trainer and optimizer; all 290 initial trainable parameter names, shapes and value hashes matched. Every one of eight steps in each runtime had 290/290 finite CUDA gradients, with nonzero gradient norm. Native changed 252 model parameter hashes and strict shim changed 247. First-two versus last-two mean training loss fell from `-0.001905085` to `-0.024701715` natively and from `-0.005670545` to `-0.074094535` under shim. The first sampled pair had per-token RLOO advantages `+5/-5` natively and `-10/+10` under shim, demonstrating an unnormalized leave-one-out reward difference. Strict shim recorded `cuda=1 fallback=0` at process start and end.

The two public runs sampled different completion token IDs despite identical initial weights, seed and prompt; their per-step loss and gradient values are therefore separate convergence evidence, not same-input numerical parity. To close L1, worker job 23796 loaded the model through ms-swift's `get_model_processor` API and forwarded the **same captured native RLOO token IDs and mask** on both CUDA runtimes. Logits shape was `[2,50,151936]`; mean absolute difference `6.85e-6`, RMSE `1.14e-5`, and losses `1.14406240` native versus `1.14406216` shim. In the same worker job, ms-swift's `compute_advantages` API returned `[-5,5]` on CUDA for fixed rewards `[25,30]`, two generations, RLOO and no reward scaling on both runtimes; strict fallback was zero. These observations establish controlled L1 and independent fixed-window L2 without imposing stepwise equality on sampled training trajectories.

The public CLI completed but deliberately wrote no checkpoint; L3 model, optimizer, scheduler, RNG and dataloader-cursor restoration were not exercised. The existing full-model GRPO checkpoint profile needs at least 8 GiB free for its measured save peak and reserve, while this run's NFS `/home` had about 7.2 GiB free. L3 is resource-blocked for this full-tuning profile until a fresh storage preflight succeeds. Formal L4 and L5 remain open under the ordered L0–L5 contract. Job 23796's forward reuses the known Qwen2 causal-LM mechanism but uses this RLOO run's captured tokens and verifies the distinct RLOO advantage function; it is not another GRPO training experiment.

## PEFT LoRA restoration and steady performance

To exercise complete state restoration within the available persistent storage, the same public RLOO CLI ran a separate FP32 PEFT LoRA profile with rank 4 on all linear layers, two distinguishable arithmetic prompts, SGD learning rate `1e-5`, two completions and `num_iterations=2`. The initial native and shim models used the same local Qwen2 weights and configuration. The shared same-input LoRA model forward and the RLOO advantage API are covered by the earlier controlled CUDA jobs 23827 and 23796; RLOO changes advantage computation, not model architecture. The new raw run keys are `20261014-qwen2-rloo-lora-cursor-v1/`, `20261014-qwen2-rloo-lora-new-process-v1/` and `20261014-qwen2-rloo-lora-steady-l5-v1/` under `$JITTOR_LAB_ROOT/_state/ms-swift-cuda/`.

Same-process native 23889 and strict shim 23890 stopped after checkpoint-2, then resumed the **same Trainer object** to checkpoint-4. A fresh public CLI process resumed each runtime's corresponding checkpoint-2 (native 23893, shim 23894); preflights 23888 and 23892 passed. Worker verifier 23895 confirmed prompt order `2+2,2+2,3+5,3+5` in the same-process path and `3+5,3+5` in the new-process path, so the loader did not restart the dataloader cursor. Resumed token IDs and masks matched within each runtime. Every training step had 336/336 present, finite CUDA gradients, and all 336 adapter keys changed after checkpoint-2. Native resumed loss fell `0→-0.000508785`; shim same/new-process losses fell `-1.53e-5→-0.000987053` / `-9.54e-6→-0.000997543`. Native same/new final adapters matched exactly; shim maximum absolute difference was `4.43e-12`. Recomputed old-token-logprob hashes differed under shim; sampled tokens and cursor did not. Strict shim recorded `cuda=1 fallback=0`.

The checkpoint hook perturbed CPU and CUDA RNG before `_load_rng_state`; restored digests agreed across same/new-process paths and differed from the perturbations. State audit 23896 loaded each side's own serialization and confirmed scheduler epoch `2→4`, preserved SGD parameter groups, optimizer payload and CPU/CUDA/Python/NumPy RNG keys. The unchanged trainer loader's exact four-source saved-payload restoration was separately verified by GRPO LoRA jobs 23860/23861 at this implementation baseline. Together with actual adapter checkpoints, optimizer/scheduler state, global step and distinguishable cursor, L3 passes for the LoRA profile. Both sides executed the real public CLI and wrote checkpoint-2/4, giving L4 with zero fallback.

For L5, preflight 23897, native 23898, strict shim 23901 and verifier 23902 passed. Each CLI ran 14 no-checkpoint updates from the same saved adapter, with four warmups followed by ten CUDA-synchronized `on_step_begin`–`on_step_end` samples. Native mean/median/p95 was `0.113660/0.113567/0.116904` s (`8.798` steps/s); shim was `0.273470/0.273545/0.275710` s (`3.657` steps/s), a `2.406×` mean-latency ratio. Whole-device `nvidia-smi` memory readings peaked at 2750/2942 MiB and are not per-process allocations. Shim fallback was zero. The timed interval excludes initialization, cold first-step compilation and checkpoint I/O.

The NFS `/home` export is exclusive to this user and worker write probes succeeded. Same-class LoRA checkpoint run directories measured 221–241 MiB; the later RLOO preflight conservatively used a 512 MiB per-stage peak and required 3 GiB free (`2×peak+2 GiB`), with each worker rechecking free bytes and inode count. The estimate and raw probes are in `20261014-qwen2-rloo-lora-cursor-v1/storage-estimate.txt`. No model, JIT cache or evidence was removed to make space. This LoRA result does not close the separate full-tuning storage limit, mixed precision, multi-GPU or PPO paths.
