## FIPO first failure

The same real CLI with `--loss_type fipo` passed worker preflight 23917, including isolated TRL 0.26.0, native CUDA, strict shim CUDA imports, no-build JIT cache, and a worker write probe. Native public CLI job 23918 constructed the model/trainer and entered training but failed on the first policy-loss computation with `ValueError: OPD-RL (teacher) does not support loss_type='fipo' / off_policy_sequence_mask.` The traceback is retained verbatim in `20261014-qwen2-fipo-lora-loss-window-v1/native.log` under the unversioned state root. The shim FIPO training process was not submitted because the independent native reference is blocked before any valid loss or gradient exists.

This is an ms-swift guard issue, not evidence of a Jittor defect: the CLI configuration recorded `teacher_model=None`, `teacher_model_server=None` and `off_policy_sequence_mask_delta=None`, but `resolve_dynamic_opd_self_distillation()` in the ms-swift checkout returns true when there is no explicit teacher. `_setup_teacher()` then sets `_has_teacher=True` for the capability to serve a future OPSD batch, while `_compute_loss_and_metrics()` rejects FIPO whenever `_has_teacher` is true, even for this reward-only batch without a teacher signal. The first failed layer is L1 policy-loss construction. No valid CLI flag was found to disable this capability without selecting an actual teacher; no external ms-swift source was modified. Recheck only after the upstream guard distinguishes an active teacher signal from dynamic capability, then restart at a fresh short preflight. This is one confirmed root-cause hypothesis, below the five-attempt ceiling.
