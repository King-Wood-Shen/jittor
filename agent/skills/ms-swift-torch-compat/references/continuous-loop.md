# 反馈、审核与持续续接

## 使用已有总控，不建立平行指挥链

总控和执行者的对话 SID 跨调用保持不变；CLI 一次调用结束只是一次轮次结束。服务器包装器维护同一总控的持久 loop，把新的执行反馈、作业终态、用户优先级转换为下一轮输入。总控只对已结束且进程/锁已释放的原执行者续接，不打断仍有效运行的命令或训练。

优先接入既有 state/mailbox/ledger。下面是逻辑字段，不要求为已有实现再造同名格式或第二个 helper。

## 执行者反馈

每完成一项、提交作业或遇到失败，原子写出反馈并通知总控。核心字段：

| 字段 | 用途 |
| --- | --- |
| event_id、task_id、role、SID、time | 唯一归属和幂等处理 |
| kind | progress / completed / failed / blocked / job_submitted / job_terminal |
| source/dependency/input identity | 将报告绑定到真实源码和输入 |
| jobID、exit、raw evidence paths | 独立核实实际动作与首错 |
| result and remaining | 哪一项通过，哪些仍未闭 |
| question and proposal | 总控具体要判断或批准什么 |

包装器必须补报无法自行反馈的情况：命令沙箱在第一条命令前失败、模型 transport/auth 错误、非0退出、进程异常消失。不能要求已无法执行命令的模型先写一份“成功反馈”才处理。

## 总控处理

1. 收到新事件就唤醒同一总控；已有总控活动时将事件排入队列，不并行启动第二个。事件在 **决定已持久化** 后确认，防止崩溃后丢消息。
2. 读取原始证据，绑定当前 task/source/job；对反馈作出具体决定：修复方向、受影响验证、资源动作、下一任务，或可核实的真实依赖等待。
3. 在原执行者收件箱记录 decision_id、关联 event_id、目标 SID、任务、验收边界、文件归属和必要资源。能由总控处理的技术问题直接答复，不转交本地做例行决策。
4. 包装器核原进程与锁后续接；执行者记录已读决定及首个实际动作。发送成功不等于已执行。
5. 运行中的 Slurm 作业按 jobID 观察，首次终态只收一次；回到反馈处理。未知 job 状态不能自动认定失败或再次申请。

## 不让轮次边界造成停工

- 未处理事件、READY 待审、作业终态待收、可执行且已退出的执行者，均是立即处理条件；不固定睡30分钟。
- 没有新事件且作业都正常运行/排队，或所有剩余项都有具体外部依赖时，可以事件等待；30分钟做兜底 reconcile。
- 心跳只报“活着”不算进展。使用最近成功命令、文件/结果变化、作业状态与下一负责人判断。长 JIT/训练有正常进度时合理等待，不因一段时间无模型回复就重复启动。
- 硬认证/额度/模型不可用：保留事件、报告具体阻塞，不紧密循环重启。其余可用执行者和独立工作继续。
- 防重锁忙是有效状态，不是故障；获取锁的探针自身不能被当成新 worker。原始 job claim 不因失败而删除，修订请求用新 ID 并引用旧证据。

## 持久 loop 的最低运行验收

总控负责在自己的空闲边界部署/修复包装器，再做有边界的实际验证：

1. 现有真实反馈到达 → 唯一总控收到 → 可执行决定落盘 → 原执行者收到并执行真实命令。
2. 执行者完成/失败反馈 → 同一总控无需等待30分钟就处理 → 下发修复或下一任务。
3. 同一事件重复投递不重复派工/提交；原执行者仍活跃时不多开。
4. 等待真实资源时保持 jobID 对应的等待，不重复申请；任务结束后的输出错误能被包装器捕获。

优先用已经存在的反馈和已授权定向诊断验证，不能为了证明 loop 重跑已通过完整模型。若没有可合法执行的下一项，清楚写阻塞，不能制造空作业。上述验证证明调度闭环，不替代算法或恢复验收。

本地监控只验这些回执和进展；不直接编辑 worker、提交业务作业或提供技术答复作为闭环前置。
