# 最大有效并行调度

## 目标与固定边界

用户要求在两端可合法使用的资源内最大化适配并行度。总控各Astra low，执行者各三个Luna medium；本地只监控。目标模型是完整DeepSeek-V2-Lite Base16B MoE，任务是ms-swift的算法、优化和开关，多rank训练/恢复优先；本轮验收为L1、L3有效收敛和L5真机零fallback，L2严格对拍与L4性能暂不作前置。

最大化的是**有明确适配目标的实际并行工作**，不是对话数量、重复试验数或空占资源。角色数量不限制job数量：一个执行者可准备、跟踪和收取多项独立实验。总控协调源码所有权和依赖，不让多个执行者改同一文件；耗时实验运行时，执行者可处理独立最小复现/补丁/下一项。

## 任务板与依赖

接入已有任务账本，不再造相互冲突的注册表。每项至少包含：任务ID、模型配置、方面（算法/优化/开关）、owner、源码与输入、真实训练拓扑、资源需求、依赖、jobID/claim、验收目标、反馈/下一动作。

逻辑状态为：

```text
待定位 → 可执行 → 待调度 → 已提交/排队 → 运行 → 待收取/审核
                                    ↘ 失败定位 → 修复 → 受影响复验
                                                  ↘ 通过并交付
```

状态名称可沿用当前系统。关键是 `READY` 不是完成，`WAITING` 必须有具体依赖与解决负责人，`COMPLETED` 只说明作业结束，产品通过必须有对应收敛/功能证据。

依赖按实际调用路径建立：例如共享Trainer累计loss错误可阻塞使用该路径的训练，但不阻塞独立AdamW状态或分布式通信诊断。PPO reward/value缺失不阻塞ORPO/GRPO/GKD等其它独立任务。不能把“第一项没过”泛化为全局串行门。

## 每次事件后的调度

1. **收结果**：查新反馈和首次job终态，核首错/真实证据，将每项交给负责执行者修复或判通过；原始claim保留。
2. **盘资源**：核当前自己及节点已分配GPU/NPU、CPU、主存、分区时限、用户/QoS限制、排队原因与设备实际占用。配额未知如实记录，不能从queue为空推断到上限。
3. **选就绪项**：优先用户指定多rank训练/完整恢复；其次解除多个任务的共同兼容故障；同时安排其它独立算法/优化/开关或必要定向诊断。真实资源暂缺时可提交合法排队请求，并处理不依赖该资源的工作。
4. **提交并行任务**：不同任务/配置、独立输出与私有写缓存、冻结源码和输入可并行运行。明确每项资源用途；不空占卡、不重复申请、不触碰他人作业。两端独立推进，不因一端不可用停另一端。
5. **续接执行者**：有具体未闭工作且原SID/锁空闲就续接；已有exec或job在推进不重复拉起。执行者负责反馈，总控负责决定，不等待本地审批常规技术事项。
6. **确认生效**：记录实际jobID/排队原因或执行者已读决定与首个真实命令。未能提交则保留首错，交给负责者修复提交路径，不无期限停在同一schema/权限检查。

独立小任务可回填暂时不能满足大任务的碎片资源，但不能为“有卡在用”跑无关试验、重跑已通过项或把复制式推理当多卡训练。大任务继续合法排队。

## 多卡资源必须匹配实际拓扑

- 单进程4GPU放置记录为world1；双rank各用2GPU才记录world2/4GPU。每rank资源由完整权重、激活、优化器/teacher/reward/value实际需求决定，不能盲目一rank一卡。
- 普通DDP复制模型，不减少每rank模型内存。PPO多模型布局需真实方案；资源不足时推进前置与独立任务，不提交必然错误的占卡作业。
- 同节点/跨节点、通信后端、rank到设备绑定与checkpoint拓扑必须在请求中明确。不要因为helper只支持单节点就把多节点请求假写成单节点；总控在当前授权内修实际调度路径并核验。
- 同一源树有测试或写入时，不并发整合源码。提交后的任务固定源快照，后续修复在负责的隔离工作树上验证。
- 私有缓存与输出隔离；真正共享的编译器临界区用局部锁串行，不能把整个训练批次都放进编译锁。cache复制是否命中以日志为准。

## 连续运行与故障处理

反馈/退出/作业终态触发同一总控立即处理；无事件时轻量等待，30分钟兜底reconcile。不为维持活跃而持续调用模型空转；运行中的长训练/JIT有进度就等待。

瞬态基础设施错误保留证据并有界处理；硬认证/额度/模型错误不重启风暴。独立角色可继续。总控拥有用户授予的完整执行权限，可以实际审核、提交、修复协调运行时；这不授权读取输出凭据、干预他人作业、reset dirty、强推或推官方。

## 总控向监控汇报

汇报只需能判断实际推进：

- 各执行者实际模型、当前任务与最新成功动作；
- 正在运行/排队的job及实际GPU/NPU数量和拓扑；
- 有可执行任务却未提交的具体原因及负责人；
- 新兼容修复、收敛/恢复结果、提交/推送；
- 真正需用户决定的需求或外部阻塞。

“全部WAITING、队列为空且有READY待审”是调度待办，不是健康运行。总控须处理这些事件后再空闲等待。
